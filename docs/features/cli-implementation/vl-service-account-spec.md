# veritaslock-cli (`vl`) — Phase 4: `vl service-account`


> **Naming note:** the command surface was later restructured — `vl identity` folded into `vl usr-acct` / `vl svc-acct`, `vl user` → `vl usr-acct`, `vl service-account` → `vl svc-acct`, and `vl org` moved to the `--as` auth model. Behaviour, schema, and rationale below are unchanged; see `vl-command-restructure.md` for the mapping.
**Status:** Draft for implementation
**Part of:** the larger `vl-cli-phase1-crud-spec.md` effort, broken out as its own standalone document. Depends on `vl-env-spec.md` (Phase 1), `vl-org-spec.md` (Phase 2), and `vl-identity-user-spec.md` (Phase 3) — this document adds one table (`svc_acct`) and reuses the common `identity` and `token_cache` tables Phase 3 already built. **Does not reuse `org_membership`** — see §2's note.
**Builds on:** the live `ServiceAccountController` on the IdP (`create`, `get`, `list`, `update`, `provisionPublicKey`, `delete`), and `provision_service_account.sh`/`deprovision_service_account.sh`/`gen_assertion.py` as the reference implementation being replaced. Also depends on `idp-service-account-org-dto-fix-spec.md` landing server-side — see §5.1's note on the create payload shape.

---

## 1. Scope

This document covers:
- The `svc_acct` extension table (1:1 with `identity` rows where `kind='SERVICE_ACCOUNT'`), mirroring `user_acct`'s role for the `USER` kind.
- Extending `vl identity import` (deferred from Phase 3 §8.4) to accept `--kind SERVICE_ACCOUNT` — the primary way `SYSTEM` and other pre-existing service accounts finally get adopted into the local store, replacing the interim `VL_SYSTEM_CLIENT_ID`/`VL_SYSTEM_CLIENT_SECRET` env-var bootstrap.
- The `vl service-account` command group: `add`, `show`, `list`, `update`, `delete`, `get-assertion`. (`rotate-keys` was specified in §5.5 but **removed** — see that section and [svc-acct-key-rotation-gap.md](svc-acct-key-rotation-gap.md).)

**No tier concept for this kind:** unlike `USER` (§7 of Phase 3), service accounts are never interactively logged into — `svc_acct.client_secret_plaintext` is always populated, whether generated by `vl` at creation or supplied at import. Every service-account identity behaves like a tier-1 `USER` identity for token-acquisition purposes (§6).

## 2. Schema: `svc_acct`

| Field | Type | Notes |
|---|---|---|
| identity_id | integer | PK, `REFERENCES identity(id) ON DELETE CASCADE` |
| org_name | text | direct reference to the service account's one org — `REFERENCES organization(environment_name, name)` (via `identity.environment_name`). **Not `org_membership`** — see note below. |
| client_id | text | `NOT NULL` — same value as `identity.server_id`/`identity.principal_name` for this row (§4 step 5, §5.1 step 9), duplicated here so it's discoverable directly off `svc_acct` without knowing `identity.principal_name` is where a `SERVICE_ACCOUNT` row's `client_id` lives (`vl-identity-user-spec.md` §3). Set once at creation, never updated — there's no rename path for a service account's identity, so this can't drift from `identity`'s copies. |
| client_secret_plaintext | text | NOT NULL — always populated (§1) |
| public_key_path | text | nullable — set once a keypair is provisioned |
| private_key_path | text | nullable — path under `~/.config/vl/keys/<client_id>/private.key`, not raw key bytes in the DB, same convention as everywhere else in this store |
| key_version | integer | nullable, mirrors the server's `keyVersion` |

1:1 extension of `identity` rows where `kind = 'SERVICE_ACCOUNT'`. `ON DELETE CASCADE`, same reasoning as `user_acct` — this row has no independent meaning without its parent `identity`.

**Why `org_name` lives here directly, rather than in `org_membership` (Phase 3 §4):** `org_membership` models an n:n, role-based relationship — correct for users, who can belong to multiple orgs with different `OrgRole` values. A service account's org relationship is flat and roleless: one `orgId` set directly on `ServiceAccountEntity`, no `OrgRole`, no `user_org_role` row at all (confirmed — see `idp-service-account-org-dto-fix-spec.md`, which removes the vestigial, always-discarded `role` field that used to appear on the *create request* for this same reason). Reusing `org_membership` here would mean storing a `role` column that's permanently meaningless for this kind — the same shape of problem being fixed server-side, just relocated into the local store. A direct `org_name` column on `svc_acct` matches the real relationship instead.

No schema change needed to `identity` itself — its `kind` `CHECK` constraint already includes `'SERVICE_ACCOUNT'` (Phase 3 §3, added in anticipation of this document).

## 3. Schema version

Bump `PRAGMA user_version` to `3` (from `2`, confirmed as the store's current version after Phase 3) when `svc_acct` is created.

## 4. `vl identity import` — extending the `--kind SERVICE_ACCOUNT` path

Phase 3 §8.4 specified `--kind USER` only, deferring `--kind SERVICE_ACCOUNT` to this document. Full signature:

`vl svc-acct cache --client-id <id> --secret <secret> [--label <label>] [--private-key-path <path>] [--env <env>]`

> **Naming note:** since the [command restructure](vl-command-restructure.md), this is
> `vl svc-acct cache` (was `vl identity import --kind SERVICE_ACCOUNT`). The
> `--public-key-path` flag was **removed** (see step 6), and `--label` is now
> **optional** — it defaults to the slugified server-side display name, same as
> `vl svc-acct add`.

1. **Validate before storing** (same principle as the `USER` path): call `POST /auth/service-account/token` with `{clientId: <--client-id>, clientSecret: <--secret>}`. If it fails, error clearly and store nothing.
2. **Refuse a duplicate**: if an `identity` row already exists in this environment for `server_id = <--client-id>` with `kind='SERVICE_ACCOUNT'`, error naming its current label (same guard as the `USER` path, §8.4 step 3).
3. `GET /v1/service-accounts/{client-id}` (with the token from step 1) to read the account's actual current `keyVersion` (don't assume `1`) **and its `orgId`**.
4. `GET /v1/organizations/{orgId}` (unauthenticated, `permitAll`), upsert the local `organization` cache row. If the org can't be resolved, error and store nothing — `svc_acct.org_name` is a required FK.
5. Resolve the local label: `--label` if given, else `slugify(displayName)` from the step-3 response. Error and store nothing if that yields an empty string, or if the label already exists in this environment (`assert_label_free`, distinct from the step-2 server-id duplicate guard). Then create the `identity` row (`kind='SERVICE_ACCOUNT'`, `server_id` = `principal_name` = `--client-id`, `label`) and a `svc_acct` row (`org_name` from step 4, `client_id` = `--client-id` (same value, §2), `client_secret_plaintext` = `--secret`, `key_version` from step 3). **No `--org`, no `--role` flag, no `org_membership` row** — the org comes from the server; service accounts have no `OrgRole` (see §2's note).
6. `--private-key-path`, if supplied, is **imported** — `vl` copies it into its own key store at `<store dir>/keys/<client-id>/private.key` (0600) and derives `public.key` (0644) from it, then records those managed paths on the `svc_acct` row. It does not reference the source file in place, and it does not need a separate public key (the server already has it, and the raw public key is recoverable from the seed). This gives a cached account the exact on-disk layout `add` produces, so `delete` (and any future `rotate-keys`) behaves identically for both. If omitted, `public_key_path`/`private_key_path` stay `NULL` — `vl svc-acct get-assertion` (§5.7) errors clearly if invoked against an identity with no private key recorded, rather than failing obscurely. (A token-only service account that never needs `get-assertion` doesn't need a key at all.)

This is the intended path for finally bringing `SYSTEM` (and any other pre-existing service account) into the local store — closing the "continues via bash env vars" gap noted throughout Phases 2–3.

## 5. `vl service-account`

**No caller-kind restriction, unlike `vl user add`:** `provision_service_account.sh` authenticates as `SYSTEM` — a service account — to create other service accounts, confirming there's no equivalent of `vl user add`'s "must be `kind='USER'`" rule here. `vl service-account add` resolves whichever identity is active (per §8.3 precedence) and sends the request without pre-checking its kind — consistent with the governing principle (§2 of the master spec) that authorization is the server's call, not the CLI's. (Worth a passing note: `vl user add`'s kind pre-check in Phase 3 is arguably already a mild exception to that same principle — not being relitigated here, just flagged for consistency's sake.)

### 5.1 `vl service-account add <display-name> --role <ACCOUNT|NODE|SYSTEM|INGEST_CLIENT> --org <org> [--secret <value>] [--description <text>] [--label <label>] [--env <env>]`

1. Resolve `org_id` from `--org`, upsert the local `organization` cache row if needed.
2. Generate a random `clientSecret` if `--secret` not given (`secrets.token_hex(16)`, matching `openssl rand -hex 16`).
3. `--label`, if omitted, defaults to a slugified `display-name` (strip non-alphanumeric, lowercase — same derivation convention as org `name` from `display_name`, per Phase 2 §4.1's open item; if that derivation ends up server-side for orgs, mirror whatever was decided there for consistency).
4. `POST /v1/service-accounts` with `publicKey: null`, `bootstrapHash: null`, `displayName`, `description`, `role`, `keyVersion: 1`, `clientSecret`, `orgId` — **confirmed flat**, per `idp-service-account-org-dto-fix-spec.md`: `orgMembership` is removed entirely (both `role` and `orgName` were dead, always-discarded fields; `orgId` becomes a plain top-level field like every other field on this request).
5. Server returns `ServiceAccountCreatedDto` including a `bootstrapHash`.
6. Generate an Ed25519 keypair locally (raw libsodium format: 64-byte private = 32-byte seed + 32-byte pubkey; 32-byte raw public key), write both to `~/.config/vl/keys/<server_id>/`.
7. `PATCH /v1/service-accounts/{id}/public-key?bootstrapHash=<hash>` with the base64url-encoded public key.
8. If step 7 fails, retry once automatically with the same `bootstrapHash` (only nulled server-side on success), then surface the error clearly if it still fails.
9. Store the identity locally: an `identity` row (`kind='SERVICE_ACCOUNT'`, `server_id`/`principal_name` = the returned id) and a `svc_acct` row (`org_name`, `client_id` = that same returned id (§2), `client_secret_plaintext`, `public_key_path`, `private_key_path`, `key_version: 1`). **No `org_membership` row** — see §2. Print the client secret once.

### 5.2 `vl svc-acct show <label> [--reveal-secret] [--remote | --all] [--env <env>]`
Local cached view by default (restructure doc §3). `--remote` shows only the server record; `--all` merges it with local metadata (key file paths, whether a keypair is provisioned). Secret masked unless `--reveal-secret`. On `--remote` / `--all` the local credential's server-owned fields (`role`, `key_version`) are backfilled from the response — see §5.3.

### 5.3 `vl svc-acct list [--org <org>] [--role <role>] [--status <status>] [--include-deleted] [--remote | --all] [--page <n>] [--env <env>]`

> **Revised** by the restructure (§3 of `vl-command-restructure.md`) and this
> session:
> - Defaults to the **local cached** listing; `--remote` / `--all` hit
>   `GET /v1/service-accounts` and pass through `role` / `status` /
>   `includeDeleted` / pagination.
> - `--org <name>` filters by org in every mode. Local: `svc_acct.org_name`
>   matches. `--remote` / `--all`: resolved to the org id via
>   `GET /v1/organizations?name=` and sent as the `orgId` query param (the server
>   filters on the account's flat `orgId`).
> - Every mode renders `org` and `role` columns. On `--remote` / `--all` the
>   row's `orgId` is resolved to a name via a public `GET /v1/organizations/{id}`
>   (memoised per invocation), falling back to the raw id if it can't be resolved.
> - `role` is a cached column (`svc_acct.role`, v8), populated by `add` (`--role`)
>   and `cache` (server record). On `--remote` / `--all`, `list` **and** `show`
>   backfill `role` and `key_version` into the local credential row from the
>   server response — an account cached before v8 (role `NULL`, shown as `-`)
>   self-heals on its first server view. A `None`/absent server value leaves the
>   cached column untouched; uncached accounts get no local row.
> - The `--remote` / `--all` listing also has a `cached` column (`yes` / `no`)
>   for which server rows `vl` holds a local credential, plus the pre-existing
>   `label` column (the local label, `*` if it's the default identity).

### 5.4 `vl service-account update <label> [--display-name <text>] [--description <text>] [--status PENDING|ACTIVE|SUSPENDED|DELETED] [--role <role>] [--json-metadata <text>] [--env <env>]`
`PATCH /v1/service-accounts/{server_id}` with whichever flags are supplied (partial update, `bootstrapHash` query param omitted — not relevant post-provisioning). Public-key rotation is **not** part of this command — see §5.5.

### 5.5 `vl service-account rotate-keys <label>` — REMOVED

This section's original design was wrong. It assumed `UpdateServiceAccountRequest.publicKey`
handles rotation through the ordinary `PATCH` path with **no `bootstrapHash`
needed**. In fact the server rejects *any* `publicKey` change without a *pending*
bootstrap hash, and that hash is one-time (cleared on first provisioning, never
regenerated). The IdP is also single-key — a key change is a hard cutover with no
overlap for in-flight assertions.

The command was implemented, found non-functional against a real IdP, and
**removed**. Full analysis and the server + CLI work needed to bring it back:
[svc-acct-key-rotation-gap.md](svc-acct-key-rotation-gap.md).

### 5.6 `vl service-account delete <label> [--env <env>]`
`DELETE /v1/service-accounts/{server_id}` (soft-delete server-side, `status → DELETED`), then remove the local `identity` row (cascades to `svc_acct`, `org_membership`, `token_cache`) **and** the local key directory — matching `deprovision_service_account.sh`'s existing behavior.

### 5.7 `vl service-account get-assertion <label> [--aud <url>] [--env <env>]`
Equivalent to `gen_assertion.py`: reads `private_key_path`, builds and signs a short-lived (default 300s, matching the script) EdDSA JWT assertion, `aud` defaulting to the environment's IdP service-account authenticate endpoint unless overridden. Errors clearly if the resolved identity has no `private_key_path` recorded (e.g. an imported account where key paths weren't supplied — §4 step 5).

## 6. Token acquisition for `SERVICE_ACCOUNT` identities

Extends Phase 3 §7's flow: for any resolved identity with `kind='SERVICE_ACCOUNT'`, `vl`'s own authenticated API calls use the **symmetric** path — `POST /auth/service-account/token` with the stored `client_secret_plaintext` — silently, with no TTY/prompt branch at all (no tier-2 case exists for this kind, per §1). This mirrors how `SYSTEM`'s token has always been acquired in the existing bash scripts.

`vl service-account get-assertion` (§5.7) is a distinct, explicit utility for producing an **asymmetric** assertion to hand off elsewhere (e.g. for node-side authentication) — it is not part of `vl`'s own internal token-acquisition flow and does not touch `token_cache`.

## 7. Open Items

1. **No server-side path to rotate a service account's symmetric secret.** `UpdateServiceAccountRequest` has no `clientSecret` field — only the asymmetric public key can be rotated post-creation (§5.5). If a service account's symmetric secret is ever compromised, the only remedy today is deleting and recreating the account entirely. This is a real gap in the IdP API, not something `vl` can work around — flagging it here rather than silently omitting secret rotation from this document without explanation. Worth its own IdP-side spec if this becomes a real operational need.
2. ~~`--org-role` default of `ORG_ADMIN` for `vl service-account add`~~ — **Removed, not just resolved.** Confirmed (via `idp-service-account-org-dto-fix-spec.md`) that `orgMembership.role` was always silently discarded server-side — service accounts have no `OrgRole` concept at all, only the flat, roleless org association now modeled by `svc_acct.org_name` (§2). The flag and its payload field are gone, not defaulted.
3. **`vl org add`'s `name`-derivation question (Phase 2 §6.1) affects §5.1's `--label` default too** — if that gets resolved as server-side derivation, the client-side slugification logic proposed here for service-account labels should be double-checked for consistency, not just copy-pasted assuming client-side derivation was the answer.
4. ~~§5.1 step 4's exact payload shape depends on `idp-service-account-org-dto-fix-spec.md`~~ — **Resolved: flat `orgId` field, confirmed.** `orgName` was also confirmed dead weight, not just `role` — `orgMembership` is removed entirely, not narrowed.
